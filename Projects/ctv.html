02 / Full Stack · Team Collaboration

CTV Buyer

Web Developer Intern · March 2025–Present

Shipping inside a real product team—issues, PRs, full-stack features, workers, and the communication that keeps delivery moving.

01
The Problem

Why did this project need to exist?

Campaign and operations teams needed clearer visibility into performance, and the product needed systems that could react to events—not only display them. Manual updates and one-size-fits-all views left people hunting for the signal that mattered to their role.

02
The Approach

How did I approach it?

I worked the way the team works: track issues, communicate blockers and tradeoffs, open and review pull requests, and ship full-stack changes that include background workers—not just UI.

  • Own tickets end-to-end with clear status and review habits
  • Design for role-specific views so each user sees what they need
  • Prefer event-driven paths (webhooks, notifications, email) over manual refresh loops
  • Use agentic workflows with tools—not ML—to automate repeatable actions
03
The Build

What did I actually create?

  • Full-stack features across TypeScript/React UI and Java services
  • Background workers for jobs that shouldn’t block the request path
  • Webhook integrations that respond to external and internal events
  • Automatic emails and a notification center for timely, role-aware signals
  • Agentic tool-based workflows that take actions on behalf of users
  • Dashboards, API-driven campaign tracking, and interactive regional maps
04
The Result

What came out of it?

Features that fit how the team actually delivers software: reviewable PRs, tracked issues, and product surfaces that differ by role. Users get notified when something matters; workers and webhooks keep systems current without constant manual babysitting.

The other outcome is practice—communicating inside a team, not only coding alone.
